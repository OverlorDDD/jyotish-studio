# Stage JQA-3 — Reproducible JHora Reference Corpus (2026-10-23)

## Головна проблема
JQA-2 підтвердив збіги D1/D9/D10 на **одному** зовнішньому експорті за діагностично підібраним профілем, але не підтвердив до 1″ сидеричну лагну, True Rahu/Ketu та параметри Вімшоттарі. Немає оригінального `jhora.ini` для цього історичного кейсу. Це **прогалини зовнішніх даних і методу**, не привід міняти очікування тестів або виробничу методику.

## Центральна ідея
Запускати справжню настільну JHora 8.x під Wine із фіксованим `jhora.ini` і JHoraKit/AutoHotkey v1; безпосередньо зберігати `chart_data.txt`, `divisionals.txt`, `chart.json`, `input.jhd`, **оригінальний INI та контрольну суму виконуваного JHora** для кожної карти. Порівнювати цей незалежно отриманий набір із фактичними значеннями Galaxiora на тому самому UTC. Всі розбіжності залишаються видимими до усунення.

## Що реалізовано
- `tests/fixtures/jhora-corpus/manifest.json`: фіксує джерело, SHA-1 Git blob еталона, тип доказу, відомість оригінальних налаштувань. Тепер є **1 справжній зовнішній запис**, а не 20.
- `tools/jqa3-corpus.mjs`: `audit` запускає Swiss Ephemeris і порівнює 10 тіл та лагну, D1/D9/D10, значення в кутових секундах, махадаші та антардаші; `certify` повертає помилковий exit code, якщо немає достатніх незалежних чисел. Значення UNVERIFIED чи CONFIGURATION_DIFFERENCE НЕ можна перетворити на PASS.
- `tools/jqa3-corpus.mjs import <capture-dir> <fixture-path>`: перевіряє наявність **оригінальних** п'яти файлів із JHoraKit, INI, JHora executable SHA-256, версію, UTC і локальний час, вузли, знаки D1/D9/D10, повні 9×9 даші. Фіксує SHA-256 кожного сирого файла. Розбіжність між `chart.json` та сирими обчисленнями → помилка.
- `register`: автоматично додає імпорт до корпусу з SHA-1 Git blob, лише якщо всі сирі файли збережено й їхні SHA-256 збігаються.
- `tests/fixtures/jhora-corpus/capture-matrix.psv`: 20 **синтетичних** комбінацій часу й координат, вибраних для покриття лагн; це не еталонні результати. Це **план входів**, не сфабриковані результати JHora. Далі потрібно докрити усі 12 знаків лагни й межі варг, якщо 20 кейсів дадуть недостатнє покриття.
- `tools/jqa3-capture.sh`: запускає JHoraKit на **реально встановлених** JHora/Wine/AutoHotkey; автоматично робить резервну копію INI, повертає її навіть після помилки, не перезаписує оригінальні експортовані дані, захищає від старих виходів, фіксує справжні результати та реєструє їх. Не завантажує власницькі Windows-бінарники в репозиторій.
- `tools/jqa3-corpus.test.mjs`: перевірка provenance, byte-for-byte fixture, fail-closed поведінки й відсутніх INI.
- `npm run test:jqa3:corpus` та `npm run jqa3:audit` у `test:all`; `npm run jqa3:certify` — **окремий суворий бар'єр релізу**. Він має бути НЕПРОЙДЕНИМ, якщо даних бракує.

## Як відтворювано отримати нові незалежні еталони
Потрібне середовище, в якому встановлено **справжню JHora 8.0**, Wine (для Linux) або еквівалентний Windows-середовище, AutoHotkey v1 і Swift 6.2+ (JHoraKit). Для реалізованого batch-сценарію потрібна Linux/Wine конфігурація. В окремій безплатній локальній або self-hosted CI машині:

```bash
git clone https://github.com/normalmystic/JHoraKit.git jhorakit
git -C jhorakit checkout f63826b501eabe69c6b08c5365875e1e2f74c24a
export JHORAKIT_DIR="$(pwd)/jhorakit"
export WINE_PREFIX="$HOME/.wine"
export JHORA_VERSION="8.0.0.0" # тільки якщо справді така встановлена версія
bash tools/jqa3-capture.sh
npm run jqa3:audit
npm run jqa3:certify
```
Сценарій НЕ може завершитися за відсутності реального JHora: запобіжник проти створення псевдоеталонів. Середовище, доступне лише через GitHub API, не містить встановленої настільної JHora, тому **не можна повідомляти, що її вже запущено**. Збереження INI потрібне, бо JHora переписує його при закритті. Дані після захоплення повинні бути закомічені для CI; приватні дані користувачів не входять у публічний корпус.

## Які профілі потрібно розвести
1. `PRODUCTION`: SWISS Traditional Lahiri, apparent, geocentric, mean nodes, D10 1–9, рік 365.2425 днів.
2. `REFERENCE`: окремий запуск JHora з документованими рівно такими самими параметрами, включно з параметрами обчислення лагни та Вімшоттарі.
3. `DIAGNOSTIC`: True Citra, true positions, true nodes, D10 5–8 — вивчати окремо, **не видавати за виробничий збіг**.

Незалежний експорт Ганді в попередніх етапах, відповідно до JHoraKit reverse engineering, має True Chitra + True Rahu + D10 (5–8). Swiss `SIDM_TRUE_CITRA` та JHora True Lahiri *не гарантовано тотожні*. Положення лагни з `houses_ex(..., SIDEREAL)` і `tropicalAsc - ayanamsa` не тотожні за всіх методів. Місячний вузол старої карти може використовувати Moshier fallback замість Swiss file ephemeris. Все це потрібно явно фіксувати, а не ховати.

## Чому Вімшоттарі досі не PASS
Для повного збігу потрібен **від JHora, а не з нашого коду** зафіксований тип року, параметри старту, точна довгота Місяця, дата першого періоду та всі 81 антардаша. Поточний імпортер НЕ ставить `dashaYearVerified:true` без окремого задокументованого запису налаштувань. Числове порівняння даш є, але сертифікація не допускається без доказу конвенції.

## Критерії завершення — суворі
| Розділ | Критерій |
|---|---|
| Джерела | ≥12, ціль 20 різних **реальних** JHora експортів (з INI та оригінальними файлами); без дублювання подій народження |
| D1 | 10/10 лагна+9 тіл на кожній карті, тій самій методиці |
| Довготи | 10/10 з `≤1″` лише за однакової епhemeris/precision |
| D9, D10 | По 10/10 на кожній карті, явно однаковий алгоритм |
| Управителі | 12/12 при ідентичній домовій конвенції та зовнішньому підтвердженні |
| Накшатри й пади | 9/9, із прикордонними значеннями |
| Вімшоттарі | 9/9 махадаш і 81/81 антардаш, узгоджена точність дати |
| Покриття | 12 лагн, часові пояси, DST, ретроградність, вузли, межі D9/D10, історичний/сучасний діапазон |
| Регресії | Full `test:all`, production build, PostgreSQL API та реальні browser E2E — усі PASS |
| Реліз | Якщо чогось бракує: `NOT_CERTIFIED`, не 10/10 і не «повністю перевірено» |

**Важливо:** поточний `audit` перевіряє числову відповідність D1/D9/D10 і даш; повне зовнішнє підтвердження управителів та накшатр/пад у самій JHora збережене як окремий критерій релізу. Не вважайте саму умову `certify` достатнім доказом для цих поки неавтоматизованих критеріїв — їхня перевірка буде розширена після отримання першого INI-attested корпусу.

## Безпека виробничого рушія
Не змінено D10 1–9, mean-node за замовчуванням, Reader v6, LLM, Таро чи контент. Якщо подальше незалежне порівняння покаже реальний дефект у формулах, окремо виправити, додати тест та версіонувати/інвалідувати застарілі карти й LLM-тексти.
