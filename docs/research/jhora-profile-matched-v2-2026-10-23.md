## Product problem and why previous 8/10, 7/10 were misleading
We compared **different chart conventions**: Galaxiora's classic Swiss Lahiri/mean Rahu/D10(1-9) against a JHoraKit desktop snapshot using True Chitrapaksha/true Rahu/D10(5-8). D9 differs for Rahu/Ketu and D10 differs for Sun/Moon/Saturn. All five are expected method differences, *not five confirmed bugs*.

**Strong requirement:** never change a user's birth chart or Jyotish interpretive source merely to make the display score 10/10. Always calculate both sides under the **same explicitly named mathematical convention**. A sign-level match is not automatically sub-arcsecond astronomical equivalence.

## Next confidence gate: matched-astronomy and dashas across 10–20 separate real exports
The independent source contains ONE authenticated capture. Our new grid tests exercise 1740 distinct longitude positions but are *not* 1740 real JHora outputs. To justify public claims such as "all JHora positions verified to one arcsecond", we need:
1. 10–20 **separate captured JHora exports**, including extreme dates, DST, near nakshatra/varga boundary and different ascendants.
2. Capture `jhora.ini` with each export, explicitly matching Lahiri/Mean Node/D10/dasha-year settings.
3. Strict body-by-body angular residual <=1 arcsec (when both use the same ephemeris version and flags), exact D1/D9/D10 signs, dasha starts within mutually specified temporal tolerance; full scan of required chart facts.
4. Keep that numeric gate separate from the report text quality gate and licensing review.

This is a real research limitation, not a reason to force a misleading 10/10 using two different conventions.
