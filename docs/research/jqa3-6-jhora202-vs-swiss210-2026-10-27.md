# JQA-3.6 matched old-DLL investigation (2026-10-27)

## Crucial new independent source
The **official** JHora 8.0 release notes at https://vedicastrologer.org/jh/update_8.0.htm explicitly state:
- the application upgraded embedded Swiss Ephemeris to **2.02.01** and JPL baseline **DE431**;
- corrected an issue with non-fixed-star-based traditional Lahiri while using mean/true tropical solar dasha year definitions.
Hence comparing current Python Swiss **2.10.03** to an unknown old `swedll32.dll` (especially a 1.78 file) does **not** yet test same-source precision.

User-provided 32-bit PE32 DLL (analyzed statically, **not executed** by the server):
- size 495616 bytes, PE header compile timestamp 2012-09-11;
- contains ASCII `1.78.00` and exports `_swe_version@4`, `_swe_calc_ut@24`, `_swe_houses@36`, `_swe_get_ayanamsa_ut@8`;
- SHA256 `915c9d66188d192dfc417b251fc5da591214aa1bdf793645b6881ba0e3ec8bc8`.
These artifacts establish likely Swiss **1.78**, not binary identity with the JHora **2.02.01** that created original captures. The file is kept **out of the repository**, and is not a production dependency.

The provided https://github.com/aloistr/perl-sweph README is the Perl wrapper for **2.10.03**, not JHora source. Its `Changes` documents the arrival of `swe_get_ayanamsa_ex_ut` in **2.02 (2015)**. Wrappers and headers inform API compatibility; they do not reproduce the archived JHora DLL. https://astrozet.net/forum/viewtopic.php?t=565 describes ZET **2008** updating its Swiss DLL by a **29 August 2008** file; ZET is a different application and cannot attest JHora 8's backend.

## New actual ABI experiment (Windows)
`tools/jqa3-legacy-dll-probe.ps1` runs **only under 32-bit Windows PowerShell** and P/Invokes the declared Swiss DLL exports. It reads the **twenty untouched JHora original fixtures** and returns exact unrounded ascendant/Moon discrepancies, actual returned ephemeris flags and fallback detection. It does not edit any source or promote a candidate mode.

Required before claiming JHora-matched results:
1. Obtain **exact JHora installer** used for SHA-pinned captures (the JHora exe hash is `3ddbe5fb0458ad1f0ad91b002c7efb8bba9f08891d3f46190aba97d570b17908`).
2. Record installed `bin/swedll32.dll` hash and function `swe_version()`. Match **2.02.01** and capture original ephemeris files (DE431-related) or demonstrate returned SWIEPH vs fallback MOSEPH.
3. Run the new probe under 32-bit PowerShell with that original DLL and *the original data files*. An unrelated 1.78 DLL is diagnostic but can never prove parity.
4. If the newer release outputs all 20 positions, document source algorithm differences and adopt a documented production Swiss configuration. Ensure old persisted charts get explicit version migration; all other planets, signs and DST remain stable.

## Vimshottari
The JHora 7.65 official release notes https://www.vedicastrologer.org/jh/update_7.65.htm list **four** different solar-year modes (mean/true tropical/sidereal), unlike a single 365.x-day scalar. The original INI value `YearDefinition=0 3` must be mapped **to one of these methods by GUI/tool evidence** before calendar-parity certification. Even the best previously tested constant year gives only **43/180** major and **340/1620** subperiod date matches. Therefore switching 365.2425 to 365.256364 is not a justified fix. Distinguish the JHora local calendar display from UTC and preserve an original JHora exact transition instant for the same selected mode.
