# Panchanga 2.0 — P2.4 Integrated Hub (2026-11-02)

## Goal
Replace the stack of five unrelated auto-loading panels with a **single coherent observer and civil-date workflow**. P2.1 location, P2.2 live sunrise-to-sunrise timeline, P2.3 week/month and festival/phase data remain the canonical sources; new UI is additive and source-consistent, not a new speculative astrology engine.

## Implemented
1. **One observer before calculation:** hydrate the user's stored Panchanga city (or primary natal city when no preference exists) before calling /panchanga/day. No initial Kyiv-heavy sunrise calculation that will immediately be discarded for an authenticated visitor. Guests use Kyiv. A valid GalaxiNews `?date=` deep link is applied after the observer lookup. Invalid date falls back to the selected observer's current civil date.
2. **One lunar month selector** (Amanta / Purnimanta) at the hub level, reused consistently by week, month and daily events; the previous duplicated range-view selector was removed.
3. **P2.4 daily events:** a single `/vedic-calendar/overview?start=DAY&days=1&monthSystem=...` request returns lunar month, exact new/full/quarter phases and calendar festival candidates. A pure fail-closed adapter verifies matching observer timezone, coordinates, day, sunrise/sunset and all five sunrise angas against the existing `/panchanga/day` result, and independently validates a phase's observer-local civil date. No events are displayed if these contracts disagree.
4. **Progressive disclosure:** `PersonalPanchanga`, `AstronomicalEventsPanel` and `EclipsePanel` mount only when users select that module. The old auto-loaded seven-day festival panel is replaced by the integrated daily overview. The standalone module files and APIs remain for backwards compatibility. Switching to week/month unmounts all day-only modules, avoiding unnecessary duplicate Swiss computations.
5. **Observer preference writes** are serialized with last-selection-wins logic, preventing rapid changes from leaving an outdated city as the final saved location. Changing the date alone no longer PUTs a profile location. Reset-to-natal waits for outstanding writes.
6. **No duplicate lunar phase/sunrise block:** the exact P2.2 live timeline remains primary, sunrise/sunset cards remain once, and P2.4 annotates phases and observances in their own aligned section. Traditional kalas and methodology remain.
7. **UA/EN + accessible mobile:** plain text distinctions for lunar phases (astronomical) vs traditional candidate dates, keyboard-operable choices, 320px layout and accurate time-zone event labels.

## Correctness / limitation
- Calendar candidates **are not certified religious fasting, puja or Parana dates**; they may depend on local schools, daylight intervals and tithi precedence. A phase is a Swiss-backed astronomical moment, **not an eclipse prediction**.
- Verified Swiss source matching is not independent external reference certification. The pure adapter checks cross-endpoint consistency but cannot prove absolute correctness.
- Personalized Tarabala and Chandrabala require sign-in and an owned verified natal chart; guest detail view does not reveal personal data. No new auth routes, model math or migrations in P2.4.
- The daily observer's displayed "now" depends on client device time; past/future dates show sunrise values, never current status.
