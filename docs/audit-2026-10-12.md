# Calculation and UX audit — 2026-10-12

## Scope

- Input: date, local civil time, IANA timezone, geographic latitude/longitude.
- Astronomy: Swiss Ephemeris, Lahiri/Chitrapaksha sidereal, mean Rahu, Ketu opposite Rahu, geocentric apparent ecliptic longitude, whole-sign houses.
- Divisional charts: D1, Parashari D9, Parashari D10.
- Periods: Vimshottari 120-year Mahadasha and nine Antardashas per Mahadasha; **mean Gregorian year = 365.2425 days**, explicitly a convention.
- Visual: North Indian fixed-house chart (house 1 at the top), D1/D9/D10 switching, sign and planet labels; Ukrainian/English UI.

## Findings and fixes

1. **Blank natal-chart graphic**: the standalone app preserved `wheel-placeholder` styles after replacing contents with SVG. Fixed by switching to `wheel-ready`, forcing a responsive SVG with an explicit 360 × 360 viewBox, and rendering a North Indian 12-house diagram rather than the generic zodiac circle. Also updated the React/Next chart renderer.
2. **Incomplete translation**: many literal English labels lived in the HTML/React source outside the dictionary, including coordinate labels, table headers, signs, planets, chart summaries, Dasha lords, active status and footer. Extended Ukrainian/English labels and runtime rendering. Astrology terms retained in standard transliteration only where conventional.
3. **Native adapter integration**: switched the native adapter to the documented `julianDay(year, month, day, fractionalHour)` path to make UTC conversion explicit. **Correction:** the package npm README also documents `dateToJulianDay(date)`, so its use in v0.1 was not itself proof of a bug; the native installation remains untested here. Python fallback was already performing real astronomy. Native Node builds still require verification on a machine with installed npm dependencies.
4. **Ascendant parity**: PySwissEph `houses_ex(..., FLG_SIDEREAL)` and tropical Ascendant minus Lahiri may differ by a few arcseconds because the sidereal house routine includes additional details. Do not claim exact parity near sign boundaries until cross-checked on both backends.
5. **Dasha convention**: changing the day-count convention (360 / 365.2425 / 365.25) changes dates. Current `365.2425` setting must be displayed and compared only to calculators configured with the same year length.
6. **Verification limitations**: unit tests and standalone API run here; the full Next.js/NestJS build cannot be certified without npm installation. Independent JHora/AstroSage numeric golden charts have not yet been signed off. Do not represent this as independently validated Jyotish software.

## Verification strategy before claiming correctness

1. Build an **anonymous golden-fixture corpus**: UTC instant, coordinates, exact ayanamsa/ephemeris config, expected Sun/Moon/Ascendant + nodal longitudes, varga signs, Dasha boundaries.
2. Compare 3 public fictional cases using Jagannatha Hora (or AstroSage with same settings) against our Python Swiss backend and `@swisseph/node`. Set tolerances explicitly: planetary longitudes ≤1 arcminute, sidereal Lagna ≤1 arcminute unless precise house mode discrepancy is documented, varga signs exact except very close to a boundary, period boundaries convention-matched.
3. Add cases on the actual 3° D10 and 3°20′ D9 boundaries, DST transition, leap day, retrograde positions, and times near Ascendant sign edges. Never round before assigning signs/padas.
4. Require both browser modes (standalone and Next) to produce the same DOM-visible chart labels, table and JSON values.
5. Only after this: confidently demo as validated calculation engine; until then describe as a tested educational prototype.
